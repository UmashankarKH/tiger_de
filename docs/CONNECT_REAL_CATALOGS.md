Status of this document: the vendor facts below were checked against the vendors' public documentation on 3 Nov 2026.
The backend code (`unity_backend.py`, `snowflake_backend.py`) follows those APIs but has **not** been run against live accounts.

## 1. Databricks Unity Catalog

### Option A: Databricks managed MCP servers (no code)
Databricks hosts MCP servers that enforce Unity Catalog permissions. URL patterns from the docs:

| Server | URL pattern | OAuth scope |
|---|---|---|
| Genie (natural-language data questions, read-only) | `https://<workspace-hostname>/api/2.0/mcp/genie/{genie_space_id}` | `genie` |
| Databricks SQL (AI-generated SQL, **read and write**) | `https://<workspace-hostname>/api/2.0/mcp/sql` | `sql` |
| Unity Catalog functions | `https://<workspace-hostname>/api/2.0/mcp/functions/{catalog}/{schema}/{function_name}` | `unity-catalog` |
| AI / Vector Search | `https://<workspace-hostname>/api/2.0/mcp/ai-search/{catalog}/{schema}/{index_name}` | `ai-search` |

Good for: asking questions of governed data, and reading `information_schema`. Be careful: the SQL server can write, so connect it with a
principal that has **no** MODIFY rights if you only want it to read.

### Option B: this lab's custom server (propose/approve workflow)

```bash
pip install databricks-sdk
export CATALOG_BACKEND=unity
export DATABRICKS_HOST=https://<workspace-hostname>
export DATABRICKS_CLIENT_ID=...        # service principal (OAuth M2M)
export DATABRICKS_CLIENT_SECRET=...
export DATABRICKS_CATALOG=cpg_prod
export DATABRICKS_WAREHOUSE_ID=...
export CATALOG_ALLOWED_SCHEMAS=sales,costing
```

Grants (SQL, run by a catalog admin):

```sql
-- READ principal used by the MCP server
GRANT USE CATALOG ON CATALOG cpg_prod TO `mcp-catalog-reader`;
GRANT USE SCHEMA, SELECT ON SCHEMA cpg_prod.sales TO `mcp-catalog-reader`;

-- WRITE principal used ONLY by the approval CLI
GRANT USE CATALOG ON CATALOG cpg_prod TO `mcp-catalog-writer`;
GRANT USE SCHEMA, SELECT, MODIFY ON SCHEMA cpg_prod.sales TO `mcp-catalog-writer`;
GRANT APPLY TAG ON SCHEMA cpg_prod.sales TO `mcp-catalog-writer`;
```

Check the exact privilege names against your workspace; they differ slightly between versions and between table and schema level.

SQL generated by the backend:

```sql
COMMENT ON TABLE `cpg_prod`.`sales`.`fact_sales` IS '...';
ALTER TABLE `cpg_prod`.`sales`.`fact_sales` ALTER COLUMN `net_rev_amt` COMMENT '...';
ALTER TABLE `cpg_prod`.`sales`.`fact_sales` ALTER COLUMN `net_rev_amt` SET TAGS ('classification' = 'measure');
```

Gotcha worth teaching: in Spark SQL, escape a single quote with a backslash. Doubling it (`'it''s'`) is read as two adjacent literals.

## 2. Snowflake

### Option A: Snowflake-managed MCP server (no code)
Generally available since Nov 2025. You create an `MCP SERVER` object and list the tools it serves. Documented tool types:
`CORTEX_SEARCH_SERVICE_QUERY`, `CORTEX_ANALYST_MESSAGE`, `SYSTEM_EXECUTE_SQL`, `CORTEX_AGENT_RUN`. Access is controlled by RBAC (USAGE on the server
object and on the underlying services or semantic views). Authentication: Snowflake recommends OAuth and warns against hard-coded tokens. It supports tools only,
not resources or prompts. Sketch (verify the exact specification fields in the current docs before use):

```sql
CREATE MCP SERVER cpg_catalog_mcp FROM SPECIFICATION $$
tools:
  - name: "run-sql"
    type: "SYSTEM_EXECUTE_SQL"
    description: "Run read-only SQL against CPG metadata views"
$$;
```

### Option B: this lab's custom server

```bash
pip install snowflake-connector-python
export CATALOG_BACKEND=snowflake
export SNOWFLAKE_ACCOUNT=... SNOWFLAKE_USER=svc_mcp_reader
export SNOWFLAKE_PRIVATE_KEY_FILE=/secure/rsa_key.p8      # key-pair auth for a service user
export SNOWFLAKE_ROLE=CATALOG_MCP_READER
export SNOWFLAKE_WAREHOUSE=XS_WH SNOWFLAKE_DATABASE=CPG_PROD
export CATALOG_ALLOWED_SCHEMAS=SALES
```

```sql
CREATE ROLE CATALOG_MCP_READER;
GRANT USAGE ON DATABASE CPG_PROD TO ROLE CATALOG_MCP_READER;
GRANT USAGE ON SCHEMA CPG_PROD.SALES TO ROLE CATALOG_MCP_READER;
GRANT SELECT ON ALL TABLES IN SCHEMA CPG_PROD.SALES TO ROLE CATALOG_MCP_READER;
GRANT USAGE ON WAREHOUSE XS_WH TO ROLE CATALOG_MCP_READER;

-- A separate role for the approval CLI, with ALTER on the tables it documents.
-- Optional governance tag:  CREATE TAG GOVERNANCE.TAGS.CLASSIFICATION;  then set SNOWFLAKE_TAG_NAMESPACE=GOVERNANCE.TAGS
```

Gotcha: Snowflake stores unquoted identifiers in upper case. The backend upper-cases names in `INFORMATION_SCHEMA` lookups.

## 3. dbt

The open-source **dbt MCP server** (`dbt-labs/dbt-mcp`, run with `uvx`) exposes groups of tools: dbt CLI commands (build, compile, docs, list, parse, run, test, show),
the Semantic Layer (list metrics, dimensions, entities, query metrics), Discovery (model details, lineage), SQL (execute and text-to-SQL), Admin API and codegen.
Individual groups can be switched off with environment variables such as `DISABLE_DBT_CLI`, `DISABLE_SEMANTIC_LAYER`, `DISABLE_DISCOVERY`.
Discovery and Semantic Layer need a dbt platform token, and the Semantic Layer needs a service token.

Client config (from the project README):

```json
{
  "mcpServers": {
    "dbt": {
      "command": "uvx",
      "args": ["--env-file", "/path/to/.env", "dbt-mcp"]
    }
  }
}
```

The dbt docs warn that letting a client run dbt commands can modify models, sources and warehouse objects. Treat the CLI tools as write access.

### Recommended pattern for metadata
1. Claude reads model and lineage context through the dbt MCP server (read-only tool groups).
2. Claude drafts descriptions through this lab's `propose_metadata`.
3. A steward approves, then `python -m review.approve export-dbt <id>` prints a `schema.yml` block.
4. The block goes into a **pull request**. Code review is your approval and your audit trail.

---

## Choosing between them (decision rule for learners)

- Need Q&A over governed data, quickly? Use the **managed** server.
- Need a governed *write* workflow, masking, or your own audit? **Build custom** (this lab) and run it with a read-only identity.
- Mixed estate? Run several servers side by side. MCP hosts can connect to many at once; keep each one's permissions narrow.
